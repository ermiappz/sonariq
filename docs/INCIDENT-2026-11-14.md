# Incident 14 Nov 2026: no 3D on the live Studio, demo stuck, state leaking between models

Reported by the user from Chrome on https://34-88-130-224.sslip.io/studio after the whole-ship viewer deploy
(main `e723388`). Each item below was reproduced on this VM before anything was changed.

## 1. "3D preview not available: … [Errno 2] No such file or directory: 'node'"

**Reproduced inside the engine service's own environment**, not from a login shell:

```
$ systemd-run --user --wait --pipe -p WorkingDirectory=~/sonariq-deploy .venv/bin/python -c \
    "import shutil, subprocess; print(shutil.which('node')); subprocess.run(['node', '-v'])"
None
FileNotFoundError(2, 'No such file or directory')
```

- The running service's environment (`/proc/<pid>/environ`) has `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin`.
- Node is installed for the user only: `~/.local/bin/node -> ~/.hermes/node/bin/node` (v26.8.1). A login shell
  finds it, but a systemd user unit does not.
- `engine/sonariq/pipeline/build.py` calls `subprocess.run(["node", "scripts/node/pack_tiles.mjs", …])` as the last
  conversion step (Meshopt packing). The `FileNotFoundError` was caught in `models_api._run` and its raw text was
  written into the model status, and the portal showed that text as is.
- **Why the tests didn't catch it:** every e2e and perf run started the engine from a shell (`portal/e2e/run.sh`,
  `make api`), where `~/.local/bin` is on PATH. Nothing ran a conversion under the systemd unit, and the deploy
  script's health check only calls `/health`, which never touched the converter.
- **Impact:** every model needs a conversion on the first open, because live `data/models/` was empty and nothing
  converts at deploy time. So no visitor saw any 3D. The findings list still worked.

### 1b. Found while deploying the fix: the packer's npm packages were never installed

The first deploy with the new pre-convert step failed on every model, before anything went live, with:

```
tile packing failed: … ModuleLoader.resolveSync
```

`scripts/node/pack_tiles.mjs` imports `meshoptimizer` from `scripts/node/node_modules`, which is gitignored.
`deploy_vm.sh` ran `npm ci` only for the portal, so the deploy worktree had no packer packages. Fixing PATH alone
would have turned "node not found" into a second raw error. Fixes:

- the deploy runs `npm ci` in `scripts/node`;
- the engine's startup check also loads `meshoptimizer` from there, so `/health` reports `converter: missing` with a
  readable message when the packages are absent;
- the deploy stops if pre-conversion fails or `/health` is not `converter: ok`.

## 2. Inbox (7) and Tasks keep the previous model's items

How the state is stored (main `e723388`):

| State | Where | Scope |
|---|---|---|
| Inbox, Tasks, sidebar badge | `App.tsx` polls `GET /runs` every 2 s and shows **the newest run in the whole store** (`runs[0]`) | global |
| Studio's open model | `Studio.tsx` local `target` state; opening a model does **not** create a run | per tab |
| Task cards | `data/tasks.json`, keyed by `check_key` only | global |
| "Incorrect" marks | `data/incorrect.json`, keyed by `check_key` only | global |
| Saved views | `data/views.json`, keyed by tile id (file hash) | per file |
| Revisions (step 7) | `data/revisions.sqlite`: models → revisions; no project level | per model |
| Project | the header chip "Demo ship ▾" is static text | none |

So opening RCRV in Studio changes only Studio's local state. Inbox and Tasks keep showing whichever run was analysed
last, by anyone. That's the 7 findings of the Deck 5 Rev B run the demo had just made. Tasks and marks are keyed by
`check_key`, so they show up on any later run that happens to contain the same check.

## 3. Demo stops at step 2 of 8 "working…"; Next and Stop do nothing visible

Reproduced on the live site in headless Chromium (`scratchpad/repro.mjs`): after 20 s the bar reads `step 2 of 8 ·
working…`, the Next button is disabled (the click times out), and Stop removes the bar.

- Step 2 calls `until(() => viewer.firstFrame != null, …, 600000)`, which **polls for up to 10 minutes**. With the
  converter broken (item 1), the viewer goes to its error state and the first frame never comes. The step has no
  check that the 3D is in an error state, and no shorter timeout.
- `DemoRun` keeps `busy = true` until the step's promise settles. Next is `disabled={busy}`, and the → / Space keys
  are ignored while busy, so Next stays dead for 10 minutes.
- Stop calls `onStop()`, which unmounts the bar, but:
  - nothing cancels the running step: the 10-minute poll keeps going, and if a later step had been running it would
    keep changing the Studio;
  - nothing restores what the demo changed: open model, tab, display mode, cuts.

  After Stop, the Studio looks exactly as before Stop (the same error banner, the same model), so the click looks
  like it did nothing.
- The demo also **wrote into the shared data**: it saved a Rev A, analysed Rev B and saved a BCF revision into the
  "Deck 5 demo" model, on every play. That makes item 2 worse.
- There were no unhandled promise rejections: errors were caught, but only after the 10-minute timeout.

## 4. Nothing guides a first-time visitor

`/` showed the marketing Home page. The Studio had no hints, and the demo was the only guided path.
